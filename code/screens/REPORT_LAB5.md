# Отчёт по лабораторной работе №5

## 1. Введение и концепция управления техническим долгом

В рамках работы рассматривался переход от накопления «быстрых» решений к сознательному контролю качества кода. Согласно материалам лекции, технический долг — это цена ускоренной поставки функционала; его нужно отличать от хаоса (неосознанный долг) и планово погашать рефакторингом, тестами и дисциплиной процессов.

**Цели практической части по проекту KitchenMate:**

- снизить **связность** бизнес-логики с классом приложения `KitchenMateApp` и с GUI;
- ввести **приёмочно ориентированную проверку** для выделенных сценариев (подход ATDD: сценарий → тест → реализация → рефакторинг);
- зафиксировать регрессии при дальнейших изменениях (поиск рецептов, список покупок).

## 2. Анализ технического долга и рефакторинг

### 2.1. Выявленный долг

На этапах ЛР №1–4 в `main.py` накопилась логика, которую сложно проверять без запуска всего окна Tkinter и без сетевых вызовов: фильтрация избранных рецептов по строке запроса и слияние «недостающих» ингредиентов со списком покупок были встроены прямо в методы контроллера. Это повышало **зацепление** UI и данных и затрудняло unit-тестирование (типичный признак долга из раздела «Код / Архитектура» методички).

Дополнительно наблюдался **процессный** долг: отсутствие автоматизированных тестов для чистых вычислений.

### 2.2. Выделение модуля бизнес-логики (`recipe_utils.py`)

Для погашения долга выделен слой **чистых функций** (без побочных эффектов, без обращения к БД и виджетам):

| Функция | Назначение |
|--------|------------|
| `filter_favorites_by_query` | Локальный поиск по названию в списке избранных рецептов. |
| `merge_missing_into_shopping` | Добавление недостающих ингредиентов в список покупок без дубликатов по имени (в т.ч. согласованное сравнение регистра). |

**Принцип:** единственная ответственность (SRP) — правила предметной области отделены от отрисовки и HTTP.

### 2.3. Интеграция в приложение

Файл `main.py` обновлён: методы `search_recipes` (ветка локального поиска) и `add_missing_to_shopping` делегируют вычисления модулю `recipe_utils.py`. Объём дублирующей императивной логики в контроллере сокращён; дальнейший рефакторинг (например, вынос работы с TheMealDB в отдельный клиент) упрощается.

## 3. Автоматизированное тестирование (ATDD / приёмочные сценарии)

### 3.1. Стратегия

Для изолированных функций применена проверка по принципу **чёрного ящика**: на вход подаются структуры данных, сравнивается результат с ожидаемым. Это соответствует идее ATDD: сначала формулируется ожидаемое поведение (сценарий), затем пишется тест, затем реализация и при необходимости рефакторинг без страха сломать контракт.

### 3.2. Тестовый набор (`tests/test_recipe_utils.py`)

Реализованы сценарии:

1. **Пустой запрос** — при пустой строке запроса локальный поиск не возвращает «ложных» совпадений (граничное условие).
2. **Поиск без учёта регистра** — запрос и название рецепта в разном регистре дают корректное попадание в выборку.
3. **Слияние списка покупок** — ингредиент с тем же именем, что уже есть в списке (в другом регистре), не дублируется; новые позиции добавляются.
4. **Сохранение существующих записей** — при отсутствии новых ингредиентов исходный список не теряет атрибуты (например, флаг `checked`).

Инструмент: **pytest** (зависимость указана в `code/requirements.txt`).

### 3.3. Результаты прогона

Тесты выполняются командой из корня репозитория (рекомендуется виртуальное окружение):

`python -m pytest tests/test_recipe_utils.py -v`

На момент сдачи отчёта все перечисленные тесты завершались успешно.

## 4. Управление дефектами и качество

### 4.1. Процесс

Для учебного проекта рекомендуемый поток: регистрация несоответствия (issue / задача в трекере) → исправление в отдельной ветке → проверка тестами → слияние. Парная проверка (см. ЛР №4) снижает риск повторного внесения долга.

### 4.2. Пример устранённого дефекта класса «логика / данные»

**Симптом:** при добавлении недостающих ингредиентов из карточки рецепта возможны дубликаты строк, если имя продукта совпадает с уже имеющимся в списке покупок с отличающимся регистром (например, «Молоко» и «молоко»).

**Причина:** сравнение выполнялось не в одном месте и не по единому правилу.

**Метод устранения:** централизация правила в `merge_missing_into_shopping` и покрытие сценария unit-тестом — снижение регрессий при изменении UI.

## 6. Рефлексия и выводы

Технический долг в KitchenMate носит смешанный характер: **осознанный** (например, пользователи в JSON в `db.py` для MVP) и **требующий погашения** (логика в толстом контроллере, отсутствие тестов на правила предметной области).

**Достигнуто:**

- выделен тестируемый слой `recipe_utils.py`;
- введены автоматические проверки для критичных сценариев списка покупок и локального поиска;
- упрощён дальнейший рефакторинг `main.py` (в т.ч. вынесение HTTP-клиента).

**Дальнейшие шаги погашения долга:** унификация хранения пользователей в SQLite; CI (GitHub Actions / GitLab CI) для прогона `pytest` на каждый push; постепенное покрытие остальных правил (парсинг ответов API) тестами с моками `requests`.

Система в части вынесенной логики переведена к более предсказуемому изменению; полный «промышленный» уровень качества потребует расширения тестов и пайплайна.
